Coding agents write most of my code now.
What stays mine is everything around the code: what gets built, in what order, how we know it works and whether it merges.
I run that as a loop of stages where each one commits a file the next one reads.
The shape comes from Anthropic's AI-native SDLC playbook.
I turned it into commands, agents and hooks that I use in every product repo.

DORA's 2025 research found that AI amplifies what a team already is.
So the foundation and the gates came first for me.
Speed came after.

## Every stage leaves a file

Work starts from a real problem, written down as an intent.
The interview that produces it lives inside the product, not in my terminal.
Anyone using the product can file a bug, an idea or a change from its chat.
The chat then interviews them one question at a time: what hurts, who it touches, what is out of scope and what success looks like.
It isn't allowed to design the solution or invent a number.
Anything still unknown goes under open questions.
The result is `intent.md`, committed before anyone touches code.
When I'm the one with the problem, the same interview runs as `/intent` in Claude Code.

`/spec` reads the intent and writes `spec.md`, checked against the repo's own design, review and security policies.
Every requirement has to trace back to a line of the intent.
When something conflicts with a policy the spec lists it for me to settle.

`/plan` writes `plan.md`: the files touched, the order of work, the test behind each step, the options I rejected and the exact commands that prove it's done.
Before it shows me anything it has to answer two questions.
What might this break?
Which step is most likely to go wrong?
Nothing gets built until the plan is committed.
When the build strays from it, the departure goes into the plan in the same commit.

Then comes the diff.
A bug fix starts with a failing test, committed before the fix.
Done means the repo's verify command ran and its output is pasted into the pull request.
A sentence saying the tests passed doesn't count.

The pull request carries the review findings with it.
Someone who missed every conversation can open the folder and follow the work from problem to merge.

The agents have roles too.
A planner reads to decide and doesn't edit.
Builders write the code.
Readers search and summarize.
A review pass runs at higher effort.
Today that means Opus plans at medium effort, Sonnet builds and Haiku reads.
Risky work like security, data or anything that crosses repos gets an Opus review at high effort.
Easy work never touches the large models at all.
Each of those is a default with its reason written beside it.
Any of them can change for a given task.

## Enforcement lives in code

I learned this one the hard way.
A nightly agent in [JobbyJob](/work/jobbyjob) made up records with an instruction against making things up sitting in its prompt.
A sentence in a prompt asks.
A hook checks every time.

Three hooks ship with the method.
One blocks edits to tests while a fix is in progress, so the fix can't quietly rewrite the test it was meant to pass.
One flags code that changed with no update to the plan.
The third stops a push to main, a production deploy, a publish or a merge until a person says yes.
Each hook starts in warn mode, where it logs the call and lets it through.
Once the log shows the rule is right it flips to enforce.
The production gate already enforces.

Review follows the repo's `REVIEW.md` in three passes: bugs, security and compliance with the spec and plan.
For anything large a reviewer agent runs those passes in a fresh context, so its read isn't anchored on the author's.
Findings are input to me.
They never approve or block anything by themselves.
When the same mistake gets flagged twice it becomes a line in the repo's agent file under "Things Claude gets wrong".
Every line in that section started as a mistake.

The agents take the work as far as the gate: a branch, a pull request, green checks and every finding answered.
They don't merge.
I do.

Some of what I ship is model behavior, which a unit test can't pin down.
For that I write [evals](/writing/evals-are-the-new-prd).
JobbyJob's job scorer is the clearest case.
Its rules live in a single rubric file and nowhere else.
Every decision I make on a job lands in an append-only ledger with the scores as they stood at that moment.
A calibration script proposes a new curve from that ledger using plain arithmetic.
Nothing applies until I approve it.
When I score my own resumes, each result is stored with a hash of the rubric and of the file it read.
If a number moves I can tell which of the two changed.

## What a teammate sees

The method is open.
It ships as the `pro-ai-sdlc` plugin in [pro-dev-skillset](https://github.com/jodybrewster/pro-dev-skillset) under the MIT license.
One command, `/sdlc-init`, adds an intent folder, a `REVIEW.md` and a block in the agent file.
Everything else runs from Claude Code alone.

Accepted intents flow to mieruka, my software factory, which is Claude Code with a better face on it.
It picks each intent up, routes it to a workflow and runs the agent sessions in their own worktrees behind approval gates.
It owns no stage logic.
Anything it does can be done by hand with the plugin.
The chat framework that runs the interview is going open source soon. mieruka may follow.

On your first day with me you'd find three things in the repo: the agent file, the intent folder and `REVIEW.md`.
Each of my pull requests links to its intent folder.
The plan says where the build changed course and why.
The verify output is in the description, along with a review tally like `important: 0  nits: 2  skipped: 0`.
You can argue with any finding.
That's what they're for.
Routine engineering choices arrive already made, with the reason named.

Six commands, four agents, three hooks and a merge button only a person presses.
